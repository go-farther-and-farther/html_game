# 雨夜便利店：改进建议与 Zcode 修改任务

评估对象：当前目录的 `index.html` 与本地 `three.min.js`（r147）。

评估依据：源码检查，以及使用项目自身 Three.js 做的几何方向数值核对。本次本地页面预览被浏览器安全策略阻止，没有完成画面、交互和帧率的实测。因此，下面区分代码可确认的问题与需要实际画面验证的美术建议。尚未修改场景代码。

## 推荐方向

保留已有的三渲二微缩街角、冷蓝雨夜、暖色便利店和程序化素材。这份代码已经包含货架、售货机、自行车、屋顶设备、玻璃雨痕、积水、涟漪、滴水和蒸汽；下一阶段最有价值的是让这些元素协调工作。

可选的三条路线：

1. **氛围精修，优先推荐。** 修正空间关系，突出店铺暖光与室外冷雨，加强湿地反射和生活感。改动相对集中，也最能保留现有特色。
2. **轻互动场景，后续选择。** 点击门、售货机或关东煮获得短反馈。更耐看、耐玩，但需要处理点击与拖拽冲突，以及交互状态。
3. **写实渲染改造，暂缓。** 实时反射、完整动态阴影和更复杂材质会增加实现与性能成本，也可能改变当前风格。

## 第一轮：先修正确定的问题

### 1. 路灯光锥、灯面与地面光斑

位置：`index.html` 938–959 行附近。

- `ConeGeometry` 的尖端原本在局部 +Y，当前 `cone.rotation.x = Math.PI` 把尖端翻到了下方。已用项目本地 r147 几何数据确认。应让尖端在灯下、宽口朝向地面。
- `lampFace` 当前 `rx: -Math.PI/2` 把平面正面转向 +Y；灯底发光面应朝 -Y。可以参照同文件顶灯板使用的朝向。
- 灯头世界坐标 Z 为 `6.0 - 1.5 = 4.5`，地面 `lampPool` 中心 Z 为 `3.4`。如果保留垂直光束，应统一灯头、光锥轴线和受光区域中心；若设计成斜照，应一起调整光束轴线和落点。
- 区分“灯照亮地面的光斑”与“面向观察者延伸的湿地反光”，两者不必使用相同的形状和位置逻辑。
- 修正方向后，按灯头和承接地面的高度重新计算光锥高度与中心，避免只删除旋转后留下悬空宽口。光锥边缘应柔和，并在末端渐隐。

验收：正面、侧面、背面、俯视都能确认光从灯头向下散开；没有朝上的发光底面，也没有明显的硬边透明圆锥。

### 2. 雨粒子坐标混用，优先级很高

位置：`makeRain()`，1206–1251 行附近。

CPU 写入 `aSeed = [x0, z0, speed, length]`，因此 `.y` 是 Z 坐标，`.z` 是速度。但当前着色器在屋顶范围判断和 `vec3 p` 的 Z 分量中用了 `.z`。

结果是主雨 Z 被放到 13–19，次雨被放到 8–12，而底座只覆盖约 -10–10；屋顶 Z 范围判断也始终不成立。时间推进中 `uTime * aSeed.z` 使用速度是正确的，不能全局替换 `.z`。

要求：

- 显式命名 `x0 / z0 / speed / length`，空间计算使用位置，时间推进使用速度。
- 为每滴雨使用独立相位；目前 CPU 生成了 `off` 却没有传入，着色器拿长度推导相位。
- 遮雨范围以真实屋顶、雨棚几何为准，并考虑风造成的横向偏移；当前硬编码范围也不等于完整屋顶范围。
- 检查室内、雨棚下和底座之外是否出现不合理雨线。

验收：两层雨覆盖街角；方向一致且有速度差；屋顶和雨棚挡雨；屋檐水滴仍从边缘落下。不要仅通过增加雨量掩盖分布问题。

### 3. 自动门附件与建筑开口

位置：592、636–650、1323–1334 行附近。

- 门贴纸挂在 `store` 上，未挂在移动的 `doorPanels` 上，开门时不会随门移动。
- 正面雨痕是覆盖整面店面的固定大平面，跨过门洞；开门后门洞处仍有雨痕。
- 前裙墙是一整条横跨店面的实体盒子，也跨过了入口，需要按门洞拆分。检查门槛高度是否合理。

要求：贴纸和门玻璃雨痕属于对应门扇；固定窗雨痕按窗分块；店门开口从地面到门楣保持畅通；开关全过程检查玻璃、边框与邻窗的重叠。

验收：门打开后没有悬空贴纸、悬空雨痕或挡住入口的裙墙。

### 4. 灯光要真正影响周围材质

位置：`TOON_VERT / TOON_FRAG`、`toonMat()`、`glowMat()`。

当前自定义 Toon shader 使用固定的 `uAmb / uKey / uDir`，没有接收 Three.js 场景灯光的代码。因此，单纯添加 `PointLight` 或 `SpotLight` 不会让这些材质获得局部照明。

推荐保留当前 shader，增加少量可控的局部光照贡献：路灯照亮附近地面与物体，门口暖光影响近处墙框和地面，售货机只照亮脚边。可用距离衰减、方向衰减和少量代理阴影实现，不要求全场物理照明。

另外：

- 顶点法线当前直接乘 `modelMatrix`，不适合非均匀缩放下的一般曲面法线。应使用逆转置法线变换，并确保法线、光方向、视线处于同一坐标空间。
- `glowMat()` 没有转交传入的 `blending`，玻璃雨痕调用处的 `AdditiveBlending` 实际未生效。先确定所需混合方式，再修正工厂参数传递。
- 校准 Basic 材质与自定义 shader 的颜色输出，避免部分物体偏亮或饱和度不一致；不要直接套用其他 Three.js 版本的颜色管理接口。

验收：调低某个局部灯的强度时，相关灯面、附近受光和反光协调变化，远处物体不跟着整片变亮。

### 5. 货架与玻璃的深度关系

位置：饮料柜 679–691 行附近。

饮料柜实体中心 Z=-6.95、深度 0.95，正面位于 Z=-6.475；其展示背板 Z=-6.49、商品贴片 Z=-6.56，都位于实体正面之后。按当前不透明实体的深度关系，这些内容会被柜体挡住。

要求：用背板、侧板、顶底板构成开放柜体，或者明确把展示内容置于可见表面；同时检查冰柜等类似结构。透明表面检查深度写入和排序，不要用全局关闭深度测试来掩盖问题。

验收：从店铺可见视角放大，能看到饮料柜商品；旋转后不出现商品透墙、玻璃突然盖住所有物体的现象。

## 第二轮：画面提升，建议重点投入

### A. 明确视觉主次

目标是先注意到便利店入口与招牌，再看到路灯和地面反光，最后探索周围街道。

- 店内以柔和暖白为主，入口与关东煮带少量暖黄；避免整间店均匀发黄。
- 室外维持低饱和冷蓝灰，路灯使用另一档较暖色温，售货机少量冷白。
- 降低背景楼窗、次要霓虹与大面积光晕的存在感。先看整体明暗和色彩分组，再决定是否需要 Bloom。
- 描边有主次：建筑轮廓较明确，货架商品更细，玻璃、蒸汽和水面避免粗重黑边。
- 室内底色与主光的叠加目前较强，应结合实际画面检查高光裁切和“白成一片”，不要盲目提高发光强度。

### B. 让地面像湿路面

当前 `puddle()` 的“反射”是固定冷暖色带，没有采样招牌或场景，也没有视角关联。可以先做风格化的近似反射，不必直接实现全场镜面。

- 给主招牌、店窗、售货机和路灯各自对应的倒影形状与颜色。
- 倒影贴着地面，在积水中更清晰，在粗糙沥青上更破碎、更暗。
- 用轻微波纹扰动和纵向断续条带打散轮廓，避免单纯平滑椭圆色块。
- 光源变暗时对应倒影一起变暗；旋转相机时检查反光方向，不要让长条反光永远固定朝一个方向。
- 干燥雨棚下、普通湿地、积水三种区域应有差别。少数位置反光强即可。

### C. 让雨有空间层次

现有两层雨可以继续使用，但需要先修正第一轮的坐标问题。

- 前景雨稍长、数量少，远景雨更细、更弱，避免全屏同样亮度的白线。
- 靠近路灯的雨丝更亮，背景暗处更弱。
- 保留已有屋檐滴水与涟漪，让水滴接触地面的时刻和波纹生成对应。
- 玻璃水痕只占少量区域，并区分屋檐遮挡处与暴露处，保证能看清店内。
- 添加非常轻的远处雨雾时要注意自定义 shader 不会自动获得普通材质的雾效果，需要显式实现或保持一致的替代方案。

### D. 改善相机观赏体验

当前空闲 2.5 秒后以 0.10 rad/s 自动转动，约一分钟绕一周；对仔细看店内细节可能偏急。

- 首屏稳定展示入口、正面与右侧橱窗，按横屏和竖屏适配构图。
- 优先改成正面附近的缓慢小幅巡游，或延长空闲恢复时间到约 8–12 秒，具体以实际体验调节。
- 用户按住但不移动时也暂停自动巡游；当前仅用最后一次事件时间判断，静止长按仍可能恢复自转。
- 近距离缩放与俯仰应检查穿墙、穿屋顶及主体出框。若不提供进入室内的功能，应限制到稳定可观赏范围。
- 提供低干扰的回到初始视角方式，例如双击空白处。若增加点选互动，统一处理拖拽阈值和双击冲突。

## 第三轮：少量生活感，完成前两轮后再做

一次只选择一两个动作，避免所有东西都在动。

推荐组合：

- 一名低细节撑伞路人经过门口；进入感应范围后门开启，离开后延迟关闭。当前门按计时器反复开关，加入触发关系后会更自然。
- 店员缓慢整理一件商品，或雨棚下有一只休息的小猫；两者选一。
- 关东煮蒸汽保留低幅变化，招牌闪烁降低频率，只让一块次要旧灯牌偶尔异常，维持便利店的温暖感。
- 可选雨声、屋檐滴答和远处车声；首次用户操作后才启用音频，并提供易找到的静音入口。

低成本交互可选“点击门短暂打开”或“点击关东煮出现一缕蒸汽”，先做一种即可。交互需要短反馈和冷却，点击不能误触拖拽。

## 交付与验收要求

1. 保留修改前备份。沿用本地 `three.min.js` 与现有打开方式，不为本轮引入框架、远程 CDN 或大型资产依赖。
2. 按三轮推进。每轮完成后先运行和截图确认，不把所有需求一次性重写进单文件。
3. 固定随机种子或提供仅开发时使用的固定种子选项，让前后截图可比较；保持相同视角、窗口尺寸和动画时刻。
4. 必须覆盖：默认视角、左右侧视、背面、俯视、近距离、窄屏；特别检查灯光方向、雨分布、门洞、商品可见性和透明排序。
5. 提供同一设备、同一分辨率下修改前后的帧率或帧耗时、draw calls；尚未测量时不要声称“已优化”。性能目标应依据修改前基线确定。
6. 道具已很多，先测量绘制成本。若需要优化，优先共享材质、合批重复商品、减少小物体重复描边，并调整像素比和雨粒子数量。
7. 验收结果区分“已运行验证”和“只做静态检查”。列出改动位置、实际修复项和仍未解决的问题。

## 可直接粘贴给 Zcode 的开场任务

请阅读当前目录的《改进建议_交给Zcode.md》，在原有雨夜便利店基础上迭代。保留三渲二微缩街角、程序化素材、冷蓝室外和暖色店内的风格。

先只执行第一轮：修正路灯光锥与灯面方向、灯与光斑的位置关系；修复雨粒子 aSeed 的坐标与速度混用；修复自动门贴纸和雨痕不随门移动、前裙墙封住入口的问题；检查饮料柜展示被实体遮挡；修正材质参数传递及必要的法线问题。逐项复核现有代码，不要把行号当成不会变化的定位方式，也不要全局替换 aSeed.z，因为它在下落速度计算中是正确的。

先备份，再做小范围修改，运行后检查多个视角并报告验证结果。第一轮完成且画面稳定后，再执行第二轮的灯光层次、湿地反射、雨的层次和相机改进。第三轮生活动效最后做。避免一次性重写场景；单纯增加 Three.js 灯光无法影响当前自定义 Toon shader，需要把局部照明接入实际材质计算。
